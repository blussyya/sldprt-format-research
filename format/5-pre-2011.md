# 5. Files older than 2011

Three of the real parts are older than the `Config-N-Partition` layout. They're still OLE2 files,
but the streams that matter are compressed with **PKWARE DCL "implode"**, not zlib. That's the
old PKWARE Data Compression Library format, the one zlib's `contrib/blast` reads. Everything on
this page is from [EXP-077][exp077] unless it says otherwise.

| file | what it is | display mesh | Parasolid body |
|---|---|---|---|
| `chainwheel.sldprt` | a sprocket, 189 faces | `DisplayLists__Zip`: implode with no frame, 79,857 → 212,677 bytes | `Config-0-Body`: a u32le compressed length, then implode, 93,387 → 158,309 bytes of neutral binary (`PS`, Parasolid 13.0) |
| `plate4.sldprt` | a block with a tab, 14 faces | `DisplayLists`, not compressed | a stream named `Default`, after the configuration: a u32le length, then a bare little-endian transmit file (Parasolid 9.0) |
| `SW2000-s01.SLDPRT` | an empty part | `DisplayLists__Zip`, which unpacks to 1,697 bytes with no face records | none |

SW2000-s01 really has nothing in it. Its feature tree (`Config-0`) holds only the three default
planes, the origin and the lights, and its stored preview shows nothing but the origin triad.

## PKWARE implode

- Byte 0 is 0 or 1: literals are stored raw, or Huffman coded.
- Byte 1 is 4, 5 or 6: a 1, 2 or 4 KB dictionary.
- Then a bit stream, read least significant bit first. Each item is a flag bit, then either a
  literal or a length and distance from fixed Huffman tables. The Huffman codes are stored with
  their bits inverted. A length of 519 ends the stream.

All three streams here start `01 06`. The reference decoder, [`blast.js`][blast.js], uses every
input byte exactly on all three.

## The Parasolid body

The reference reader finds the body this way when a file has no `Config-0-Partition`: a
`Config-N-Body` stream that unpacks to a `PS` transmit file, or else a stream that starts with a
u32le length and then `B` and `: TRANSMIT FILE`. A part with no solid has neither.

**Written in schema 13006 itself** (chainwheel, `SCH_1300242_13006`, Parasolid 13.0). The schema
name has two numbers instead of three, the header has no node-type count, and no type comes with
schema data before its first node: every layout is the base one. One thing is different. LIST has
twelve fields here: the nine that later edit scripts copy, plus `current_block` (pointer),
`current_position` (int) and `finished` (logical). The names follow the XT reference. The file
parsing cleanly to its last byte confirms the layout.

**Bare binary, Parasolid 9** (plate4, `SCH_900203_9008`). It starts with `B` instead of `PS 00 00`,
the description length is an int32, and every number is little-endian. Schema 9008 differs from
13006 in five node types:

| type | difference from 13006 |
|---|---|
| BODY | no `nom_geom_state` |
| FIN | no `attributes_groups` field at the front |
| ATTRIB_DEF | no `field_names` pointer, and 13 legal-owner flags instead of 14 |
| LIST | the twelve-field layout above |
| KEY (102) | a variable-length string, not in the 13006 table |

Both files parse to the terminator with every byte used and no graph-check failures: 4,279 nodes
and 13,527 checks for chainwheel, 277 nodes and 900 checks for plate4.

Both bodies export as exact STEP, and OpenCascade reads each as one valid solid. plate4 is 14 planes
and 38,400,000 mm³, chainwheel 1,749,586.10 mm³ ([EXP-078][exp078]).

## The mesh

Two older versions of the face record from [page 2](2-display-mesh.md#face-record), both readable:

- **chainwheel** (`DisplayLists__Zip`). The 2011 record, plus two arrays between Block3 and the
  bounding record: one with a 12-byte stride and kind 100, one with an 8-byte stride and kind 8.
  Both are empty on all 189 faces. 276 strips have **control word 0** instead of 1. Every one of
  them is a 3-vertex strip, a single triangle, so the geometry comes out the same either way. What
  else the value means is open.
- **plate4** (uncompressed `DisplayLists`). Strip lengths, positions and normals, then straight
  into the bounding record. There's no Block1, Block2 or Block3, so no edge IDs. The bounding record
  starts with the u32 values 0, 1, 1 and has the box and sphere at the usual offsets (12, 36, 60,
  84).

Checks: the face counts equal the body's (189 of 189, 14 of 14), and every bounding record is
valid. plate4's mesh has the body's exact box, and its volume to float32 rounding. On chainwheel,
3,768 of 4,658 vertices lie on a B-rep surface within 1 µm. Of the other 890, 833 sit on boundary
edges, and 824 of those are the same chord points modern files have ([page 4](4-mesh-and-body.md#how-close-the-mesh-sits-to-the-surface)).
The remaining 9 boundary vertices, and 57 interior vertices up to 36 µm off, aren't explained yet.
