## 1. Question

EXP-038 states: "real topological adjacency to the new face" and "this face's own
vertices were directly, if minutely, modified by the trim" are indistinguishable for any
single edge-type feature in this corpus (fillet/chamfer/C12), because a trim that creates
adjacency to a new face is, by construction, a modification of the trimmed face's own
boundary. Given that, is there anything in the existing corpus that *can* separate
"adjacent to changed/added geometry" from "own vertices moved" — and if so, does
adjacency alone (without the face's own vertices moving) ever produce a token change?

## 2. Method

Script: `v0.4.7/exp039_direct_modification_necessity.js`. Reuses
`vertClose`/`sharedVertexCount` (copied verbatim, cited in-file) from
`v0.4.7/exp037_edge_location_and_adjacency.js`. Reads all correspondence, adjacency, and
token-changed data from `v0.4.7/EXP037_RESULTS.json`, `v0.4.7/EXP038_RESULTS.json`, and
`v0.4.7/EXP035_RESULTS.json` — no Block1/Block2 extraction, correspondence, or adjacency
logic re-implemented.

For every face recorded `identical: true` (full vertex-coordinate equality, not just
ec/vc/secCount/b1Len — this is what `facesIdentical()` in the already-validated EXP-037
script actually checks) in a modified model, computed whether it is real-adjacent (>=2
shared vertices) to any `identical: false` or newly `added` face in the same model, and
cross-referenced the already-validated token-changed verdict.

## 4. Key finding: an already-computed signal was never surfaced

`EXP037_RESULTS.json`/`EXP038_RESULTS.json` already record `identical: false` (real
vertex-coordinate mismatch) for C03/C09's +X/+Y and C12's -X/-Y — the exact faces every
prose write-up (EXP-033, EXP-037, EXP-038, and `FAILED_HYPOTHESES.md` FH-030) describes
as "not directly modified," based only on `ec`/`vc`/`secCount`/`b1Len` staying constant.
The corner vertex nearest the fillet/chamfer moves from `0.01` to `~0.009` while vertex
*count* stays 4. `FH-031` (adjacency) was corrected in place on 2026-08-14/15 once this
kind of gap was found for the adjacency test; `FH-030` (direct modification) was never
revisited with the same already-available vertex-identity signal, despite it existing in
the same JSON files since 2026-08-14.

## 5. Interpretation

- Adjacency to changed/added geometry, without the face's own vertices moving, never
  produces a token change (0/12, across fillet, chamfer, hole, and shell — extending
  EXP-037's single qualitative shell observation to a quantified, 4-feature-type result).
- Every face whose own vertices move also changes token (11/11 across all prior
  experiments' comparable data — not re-verified from scratch here, cited from
  EXP-033/037/038's own token-changed data).
- FH-030 is corrected in place: it should read Unknown/Corrected (the disproving test
  used a criterion — ec/vc/secCount/b1Len — that the same validated pipeline's own
  `identical` field already contradicts), not Falsified.
- The confound EXP-038 already identified for the co-occurring case (C03/C09/C12, where
  adjacency and direct modification pick out the same faces) is not resolved by this
  experiment and is argued, not just observed, to be structurally unresolvable for any
  feature that creates a new face by editing an existing face's boundary loop.

## 6. Limitations

- Same corpus limitation EXP-037/038 already carry: n=4 feature types, n=2 edge
  locations, all on the same 10mm cube.
- Does not attempt a new model to separate modification-without-adjacency (argued
  structurally unreachable for this feature class — see EXP039_SUMMARY.md §6).

## CORRECTION NOTE (2026-08-17, audit of EXP-037→EXP-040)

Three numerical/wording errors found on re-audit, plus one methodological finding not
previously recorded. Full derivation in `v0.4.7/EXP039_SUMMARY.md`'s matching correction
note; summary here:

1. **"11/11" (§5) is uncomputed by this script and wrong.** `rows` in
   `EXP039_DIRECT_MODIFICATION_NECESSITY.json` contains zero `directlyModified: true`
   entries by construction (the script only evaluates unmodified faces). Recomputed
   directly from `EXP037_RESULTS.json`/`EXP038_RESULTS.json`: 15 directly-modified faces
   total, 14 with confirmed `tokenChanged: true`, 1 with no archived token data (C10's own
   opening face). Correct figure: **14/14 known, 1 unknown** — not 11/11.
2. **"4 feature types, n=2 edge locations" (§6, and echoed in §3's raw-result framing)
   overstates the 12-row cell's scope.** All 12 "adjacent, unmodified" rows come from edge
   1 only (C03/C09/C04/C10); C12 (edge 2) contributes its 2 rows entirely to the 3-row
   control bucket. Two edge locations only applies to the fillet/chamfer subset, and only
   across the full 15-row dataset, not to the 12-row cell specifically.
3. **"12/12 unchanged" vs. "0/12 changed" (used elsewhere for the same 12 rows)** are
   mathematically identical but framed in opposite directions — not an error, but flagged
   given its proximity to the corrected 11/11→14/14 figure.
4. **Universal confound (new finding, not previously recorded)**: every one of the 12
   "adjacent, unmodified" rows is adjacent only to an already-*directly-modified* neighbor
   (verified against `EXP037_RESULTS.json`'s own `added[].adjacentToModelFaces`: the
   genuinely new face(s) in every model are real-adjacent only to directly-modified faces
   or, for shell, to each other — never to any face that remains in the "unmodified"
   bucket). This means §1's raw question ("does adjacency alone, without modification,
   ever produce a token change?") is not actually separable from "does adjacency to a
   directly-modified neighbor cause a change?" for *any* feature type in this corpus —
   the confound §4/EXP-038 scoped to edge-type features specifically is universal here,
   not narrowed by this experiment. The raw counts (0/12, 0/3) remain correctly computed;
   only their interpretive weight as evidence for "adjacency without modification is
   insufficient" is revised downward.

No new experiment was run to produce this note — all four items are direct recomputation
from, or re-derivation using, already-archived `EXP037_RESULTS.json`/`EXP038_RESULTS.json`.
