## Investigation 1: Hole-Diameter Relationship

### Method

Used C04 (5mm hole) and C05 (3mm hole) as primary differential. Extracted SLDPRT face structures, STEP cylinder radii, and STL mesh characteristics. Compared vertex counts on cylindrical surfaces.

### Raw Data

| Model | Hole Diameter | STEP Cylinder Radius | Cylindrical Face ec | Cylindrical Face vc | Top Face vc | Bottom Face vc |
|-------|---------------|---------------------|---------------------|---------------------|-------------|----------------|
| C04 | 5mm | 2.5mm | 70 | 70 | 62 | 64 |
| C05 | 3mm | 1.5mm | 56 | 56 | 51 | 49 |
| C07 | 5mm+5mm | 2.5mm+2.5mm | 70+70 | 70+70 | 122 | 116 |
| C08 | 5mm+3mm | 2.5mm+1.5mm | 70+56 | 70+56 | 109 | 111 |

### Analysis

**Cylindrical surface vertex count comparison:**
- C04 vc: 70
- C05 vc: 56
- vc ratio (C04/C05): 70/56 = 1.2500
- diameter ratio (C04/C05): 5/3 = 1.6667

**Linear scaling prediction:** If vc ∝ diameter, ratio should be 1.6667. Actual ratio is 1.2500. **NOT consistent with linear scaling.**

**Alternative hypotheses:**
1. **Constant chord error:** vc ∝ circumference ∝ diameter. This is mathematically equivalent to linear scaling. **NOT consistent.**
2. **Constant area per triangle:** vc ∝ √area ∝ diameter. Also equivalent to linear scaling. **NOT consistent.**
3. **Fixed angular step:** vc = constant × (something else). With only 2 data points, cannot distinguish.

**C07/C08 provides additional data points:**
- C07 first hole (5mm): vc=70 (same as C04)
- C08 first hole (5mm): vc=70 (unchanged)
- C07 second hole (5mm): vc=70
- C08 second hole (3mm): vc=56 (same as C05)

This confirms the vc values are consistent across models: 5mm→70, 3mm→56.

### Conclusion

**Status: Strong evidence (but NOT linear scaling)**

The cylindrical surface vertex count is NOT linearly proportional to hole diameter. The ratio 70/56 = 1.25 does not equal the diameter ratio 5/3 = 1.6667. With only 2 diameter values, we cannot determine the exact relationship. The relationship is NOT linear scaling.

**EXP-027 claim weakened:** "The cylindrical surface vertex count scales approximately linearly with diameter: vc ≈ 14 * diameter_mm (70 for 5mm, 56 for 3mm)." This claim is **FALSIFIED**. The ratio 70/56 ≠ 5/3.

## Investigation 2: Feature-Change Localization

### Method

Performed byte-level differential analysis on C00↔C03 (fillet), C00↔C04 (hole), C00↔C09 (chamfer), C00↔C10 (shell). Classified each changed byte range into categories:
1. geometry belonging to affected/new/removed faces
2. topology/connectivity changes
3. vertex/index renumbering effects
4. global serialization/index structures
5. metadata or bookkeeping
6. changes that cannot currently be classified

### Raw Data

| Pair | Purpose | Total Changed | size_difference | inter_face_metadata | global_serialization |
|------|---------|---------------|-----------------|---------------------|----------------------|
| C00↔C03 | fillet | 7,477 | 2,300 (30.8%) | 5,172 (69.2%) | 5 (0.1%) |
| C00↔C04 | hole | 14,218 | 6,986 (49.1%) | 7,232 (50.9%) | 0 (0%) |
| C00↔C09 | chamfer | 6,444 | 1,292 (20.0%) | 5,152 (80.0%) | 0 (0%) |
| C00↔C10 | shell | 9,413 | 5,230 (55.6%) | 4,183 (44.4%) | 0 (0%) |

**Key observation:** The majority of changes (50-80%) are classified as "inter_face_metadata" — changes between face blocks, not within them. This suggests renumbering/reshuffling effects dominate the binary diff.

### Face Start Offset Analysis

| Pair | C00 Offsets | Modified Offsets |
|------|-------------|------------------|
| C00↔C03 | 5136,6020,6904,7788,8672,9552 | 5430,6314,7198,8082,8974,10226,11474 |
| C00↔C04 | 5136,6020,6904,7788,8672,9552 | 4992,5876,6760,7644,8572,11442,14326 |
| C00↔C09 | 5136,6020,6904,7788,8672,9552 | 5430,6314,7198,8082,8966,9916,10866 |
| C00↔C10 | 5136,6020,6904,7788,8672,9552 | 5136,6364,7248,8132,9016,9900,10780,11760,12740,13720,14700 |

All face start offsets change when faces are added or modified. This means the entire DL is re-serialized, not just the affected faces.

### Face-by-Face Matching

| Pair | Matching Faces | Changed Geometry | New Faces | Removed Faces |
|------|----------------|------------------|-----------|---------------|
| C00↔C03 | 2 (faces 0-1) | 2 (faces 2-3) | 3 (faces 4-6) | 0 |
| C00↔C04 | 4 (faces 0-3) | 0 | 3 (faces 4-6) | 0 |
| C00↔C09 | 2 (faces 0-1) | 2 (faces 2-3) | 3 (faces 4-6) | 0 |
| C00↔C10 | 4 (faces 0-4) | 1 (face 5) | 5 (faces 6-10) | 0 |

### Conclusion

**Status: Strong evidence**

Feature changes are **NOT genuinely localized** to affected faces. The binary diff is dominated by:
1. **Inter-face metadata changes** (50-80%): Face start offsets, face ordering, and serialization structure change globally.
2. **Size differences** (20-56%): New faces add significant data.
3. **Global serialization** (<1%): DL header unchanged.

The DL is **re-serialized entirely** when faces are added or modified. Face start offsets shift, and all subsequent face data is rewritten. This means changes cannot be localized to specific binary structures independently of face ordering.

**EXP-027 claim weakened:** "Feature operations are localized to affected faces. Unrelated faces remain completely unchanged." This claim is **partially falsified**. While the face-level geometry of unrelated faces may be identical, the binary representation is NOT localized — the entire DL is re-serialized.

## Investigation 3: SLDPRT ↔ STEP/STL Vertex Correspondence

### Method

Extracted vertex coordinates from SLDPRT (validated parser), STEP (CARTESIAN_POINT entities), and STL (binary mesh). Compared coordinates with explicit tolerance (0.001mm = 1 micrometer).

### Raw Data

| Model | SLDPRT Vertices | STEP Vertices | STL Unique Vertices |
|-------|-----------------|---------------|---------------------|
| C00 | 24 | 27 | 8 |
| C04 | 212 | 39 | 86 |
| C03 | 60 | 33 | 28 |

### Correspondence Analysis

**C00_cube_10mm:**
- SLDPRT ↔ STEP: 3/24 exact matches (12.5%)
- SLDPRT ↔ STL: 3/24 exact matches (12.5%)
- STEP ↔ STL: 27/27 exact matches (100%)
- Max SLDPRT↔STEP distance: 0.017mm
- Mean SLDPRT↔STEP distance: 0.011mm

**C04_cube_hole_5mm:**
- SLDPRT ↔ STEP: 6/212 exact matches (2.8%)
- SLDPRT ↔ STL: 6/212 exact matches (2.8%)
- STEP ↔ STL: 30/39 exact matches (76.9%)
- Max SLDPRT↔STEP distance: 0.017mm
- Mean SLDPRT↔STEP distance: 0.010mm

**C03_cube_fillet_1mm:**
- SLDPRT ↔ STEP: 4/60 exact matches (6.7%)
- SLDPRT ↔ STL: 4/60 exact matches (6.7%)
- STEP ↔ STL: 30/39 exact matches (90.9%)
- Max SLDPRT↔STEP distance: 0.017mm
- Mean SLDPRT↔STEP distance: 0.013mm

### Key Observations

1. **SLDPRT vertices are NOT exact STEP vertices.** Only 3-12.5% of SLDPRT vertices match STEP vertices within 1μm tolerance.
2. **SLDPRT vertices are NOT exact STL vertices.** Same low match rate.
3. **STEP vertices ARE exact STL vertices** (for C00: 100%, for C04: 77% — the 9 non-matching are likely tessellation points on curved surfaces).
4. **SLDPRT vertex distances are consistently ~0.01mm** (10μm) from STEP/STL vertices. This is NOT random — it's a systematic offset.
5. **Vertex ordering is NOT preserved.** Position-ordered matches are 0% for all models.

### Interpretation

SLDPRT vertices represent a **tessellated approximation** of the B-rep geometry, NOT the exact B-rep vertices. The consistent ~10μm offset suggests:
- SolidWorks generates DisplayList tessellation with a chord-error tolerance
- The tessellation vertices are close to, but not exactly on, the true B-rep surfaces
- The tessellation is independent of the STEP/STL tessellation (different algorithms)

### Conclusion

**Status: Strong evidence**

SLDPRT vertex coordinates correspond to **generated DisplayList tessellation**, NOT exact STEP vertices or STL vertices. The correspondence is approximate (~10μm accuracy), not exact.

**EXP-027 claim falsified:** EXP-027 did not make explicit claims about vertex correspondence, but the implicit assumption that SLDPRT vertices are "exact" is **FALSIFIED**. SLDPRT vertices are tessellated approximations.

## New Hypotheses

### H1: VC-diameter relationship follows chord-error tessellation

**Status:** Hypothesis

**Statement:** The cylindrical surface vertex count follows a chord-error tessellation rule: vc = f(diameter, chord_error, angular_range). With constant chord error and angular range (2π for full cylinder), vc ∝ diameter. However, the observed ratio 70/56 ≠ 5/3 suggests the relationship is more complex.

**Testable prediction:** If we had a third diameter value, we could fit vc = a * diameter^b and determine if b=1 (linear) or b≠1.

### H2: DisplayList is re-serialized on any face change

**Status:** Hypothesis

**Statement:** When any face is added, removed, or modified, the entire DisplayLists stream is re-serialized. Face start offsets shift, and all subsequent face data is rewritten. This explains why binary diffs are dominated by inter-face metadata changes.

**Testable prediction:** If we modify a single vertex in one face, the entire DL should change.

### H3: SLDPRT tessellation uses constant chord error

**Status:** Hypothesis

**Statement:** SolidWorks generates DisplayList tessellation with a constant chord-error tolerance (approximately 0.01mm based on observed vertex distances). This explains why SLDPRT vertices are close to but not exactly on STEP/STL vertices.

**Testable prediction:** The maximum distance from SLDPRT vertices to the true B-rep surface should be bounded by the chord error tolerance.

## Remaining Unknowns

1. **Exact vc-diameter relationship:** With only 2 data points, cannot determine the exact function. Need at least 3 different diameters.
2. **Chord error tolerance:** The ~10μm offset suggests a chord error, but the exact tolerance is unknown.
3. **DL re-serialization trigger:** Is it any face change, or only topological changes (face add/remove)?
4. **Face ordering stability:** Is face order preserved across saves, or does it change?
5. **Block1/Block2 semantic interpretation:** Still unknown.

---

## Parser Implications

1. **Vertex coordinates are approximate:** Parser output should not be compared directly to STEP/STL vertices with tight tolerances. A tolerance of ~0.02mm is appropriate.
2. **Face matching requires structural comparison:** Face indices are not stable across files. Face matching must use structural properties (ec, vc, secCount, vertex positions).
3. **DL size is not predictable:** DL size depends on tessellation parameters, face count, and serialization order.
4. **Incremental parsing is not possible:** The entire DL must be parsed; cannot skip to specific faces based on offsets.
