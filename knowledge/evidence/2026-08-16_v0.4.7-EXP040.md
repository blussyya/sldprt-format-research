**Version**: v0.4.7
**Question addressed**: Follow-up to a 2026-08-16 audit of EXP-037/038 (requested review, not a

## 1. Background: What the Audit Found

A skeptical review of EXP-037 (`v0.4.7/exp037_edge_location_and_adjacency.js`,
`EXP037_RESULTS.json`, `EXP037_SUMMARY.md`) and its use throughout `knowledge/` was requested.
Two things came out of it:

1. **A legitimate, cheap next experiment**: EXP-037 computed real adjacency and face
   correspondence for all four archived pairs (C03, C09, C04, C10), but only tabulated the
   adjacency-vs-token-change cross-check for C03/C09. The same tabulation for C04/C10 was never
   built, even though every input it needs was already sitting in `EXP037_RESULTS.json`. No new
   SLDPRT file or tooling is needed to close this gap — that is what Part 1 below does.

2. **A factual error in EXP-037's own prose**, found while trying to reproduce its shell
   "contrast case" claim to sanity-check it before extending it. `EXP037_SUMMARY.md` §4 states:

   > "Shell (C10): the five new inner-wall faces ARE, by the same real-vertex-sharing test,
   > adjacent to several of the five unmodified outer walls (e.g. inner wall face 6 shares 2
   > vertices with outer walls +Y and -Y and with the modified opening face)."

   `knowledge/evidence/2026-08-14_v0.4.7-EXP037.md` §5 makes the same claim more specifically:

   > "...adjacent to several of C10's five unmodified outer walls (e.g. inner wall face 6 shares
   > 2 vertices with outer walls at C10 indices 7 and 9, and with the modified opening face 0)."

   **This is factually wrong.** Both documents' own face census (same file, §1/Section 1 tables)
   states C10's faces 6-10 are the five *new* inner-wall faces added by the shell operation, not
   outer walls. Indices 7 and 9 are therefore two of the *added* faces, not two of the five
   *unmodified* outer walls the claim needed to name. The claim cites the wrong face set as its
   own supporting example.

This matters because the "shell contrast case" — "real adjacency to a new face is not
universally sufficient for a token change" — has been repeated as a load-bearing caveat in
`FAILED_HYPOTHESES.md` FH-031, `OPEN_QUESTIONS.md` OQ-032 and OQ-036, `RESEARCH_DASHBOARD.md`,
`RESEARCH_HANDOFF.md`, and `EXPERIMENT_LOG.md`'s EXP-037 entry, every time as the reason the
fillet/chamfer adjacency correlation cannot be generalized into a universal rule. If the
underlying claim is wrong, that caveat needs re-examining, not repeating.

## 2. Method

`v0.4.7/exp040_full_corpus_adjacency_crosscheck.js`, two independent parts:

**Part 1 — tabulation, no new geometric computation.** Reads the already-committed
`EXP037_RESULTS.json`'s `matched[]` (face correspondence) and `added[].adjacentToModelFaces`
(real adjacency of each new face, already computed by EXP-037's `computeAdjacency()`) for all
four pairs (C00↔C03, C00↔C09, C00↔C04, C00↔C10). For each pre-existing (matched) face, records
whether it is real-adjacent to any new face, whether it was structurally modified
(ec/vc/secCount/b1Len), and whether its Block1 token changed — cross-referencing
`EXP033_FEATURE_STATE.json` for full token arrays, and falling back to `EXP035_RESULTS.json`'s
directly-recorded `identical` flag for C10's outer walls (whose raw token arrays were never
archived, only an identical/not-identical boolean per face — see EXP-037's own note on this
gap).

**Part 2 — independent re-derivation, deliberately bypassing EXP-037's script and JSON
entirely.** Re-implements shared-vertex counting from scratch (same tolerance, 1e-5m, same
"≥2 shared vertices ⇒ shares an edge" rule as `computeAdjacency()`) directly against
`VERTEX_ANALYSIS.json`'s raw per-face vertex coordinate arrays for the C00↔C10 pair, and checks
every one of C10's 5 new inner-wall faces (indices 6-10) against every one of its 5 unmodified
outer walls (indices 1-5) plus the modified opening face (index 0). This does not call
`matchFaces()`, `computeAdjacency()`, or read any of EXP-037's own adjacency output — it is a
from-scratch recomputation, matching this project's convention (used in the 2026-08-16 audit
itself) of not trusting a claim via the same code path that produced it.

**A bug was found and fixed in this script's own first draft**: `tokensEqual()` returns `true`
when two token arrays are identical (i.e., unchanged), but the first version of Part 1 assigned
that boolean directly to a variable named `changed` without negating it — so "tokens equal"
was being reported as "changed." This was caught, not assumed correct, by checking the first
run's C00↔C03 row against EXP-038's already-published table (`EXP038_SUMMARY.md` §"Structural
comparison") before using any of the output: EXP-038 established C03's -X face (index 0) as
UNCHANGED, but the buggy first run reported `tokenChanged=true` for it. The fix
(`const changed = isEqual === null ? null : !isEqual;`) was applied and the run repeated;
the corrected output matches EXP-038's published table exactly for every row.

## 3. Results

### Part 1: Full-corpus tally

24 pre-existing-face checks (6 faces × 4 pairs):

| | Adjacent to new face | Not adjacent |
|---|---|---|
| Token changed | **10** | **0** |
| Token unchanged | **0** | **13** |
| Unknown (no archived comparison data) | — | 1 |

The single "unknown" is C10's own opening face (C00 index 4, C10 index 0) — the directly,
structurally-modified feature face itself (the shell's opening), whose raw pre/post token arrays
were not archived (only its structural ec/vc change was). It is not a candidate "unrelated face"
test case in the first place, so its exclusion does not weaken the tally.

Per-pair detail (`C00 face (orientation): structurallyModified / adjacentToNewFace / tokenChanged`):

- **Fillet (C03)**: 0(-X) F/F/F, 1(-Y) F/F/F, 2(+X) F/T/T, 3(+Y) F/T/T, 4(+Z) T/T/T, 5(-Z) T/T/T
- **Chamfer (C09)**: identical pattern to fillet
- **Hole (C04)**: 0(-X) F/F/F, 1(-Y) F/F/F, 2(+X) F/F/F, 3(+Y) F/F/F, 4(+Z) T/T/T, 5(-Z) T/T/T
- **Shell (C10)**: 0(-X) F/F/F, 1(-Y) F/F/F, 2(+X) F/F/F, 3(+Y) F/F/F, 5(-Z) F/F/F, 4(+Z) T/T/unknown

Zero rows show `adjacentToNewFace=true, tokenChanged=false` or `adjacentToNewFace=false,
tokenChanged=true`, across all four feature types tested.

### Part 2: Independent C10 recheck

Shared-vertex counts, new inner-wall faces vs. unmodified outer walls and the opening face:

| Face | outer_1 | outer_2 | outer_3 | outer_4 | outer_5 | opening_0 |
|---|---|---|---|---|---|---|
| 6 | 0 | 0 | 0 | 0 | 0 | 2 |
| 7 | 0 | 0 | 0 | 0 | 0 | 2 |
| 8 | 0 | 0 | 0 | 0 | 0 | 2 |
| 9 | 0 | 0 | 0 | 0 | 0 | 2 |
| 10 | 0 | 0 | 0 | 0 | 0 | 0 |

Zero shared vertices between any new inner-wall face and any unmodified outer wall, in every
one of 25 pairwise checks. The only nonzero entries are each inner wall's connection to the
opening face (already directly/structurally modified) and, separately (not shown in this table,
but present in `EXP040_RESULTS.json`'s underlying `added[].adjacentToModelFaces` data reused
from EXP-037), to each other.

**This falsifies the specific example cited in EXP-037's write-up** ("face 6 shares 2 vertices
with outer walls at C10 indices 7 and 9") twice over: indices 7 and 9 are not outer walls at
all (confirmed against the face census), and face 6 has zero shared vertices with every actual
outer wall (1-5).

## 4. Final Report

### What was tested

Whether EXP-037's shell "contrast case" — cited throughout the knowledge base as the reason
"adjacency causes a token change" cannot be treated as a universal, cross-feature-type rule —
is correctly derived from the data, and whether extending EXP-037's own crossCheck to the two
feature types it skipped (hole, shell) changes the picture.

### What changed

The shell contrast case is **removed**. It was based on a claim (new inner-wall faces adjacent
to specific unmodified outer walls) that does not hold under either (a) EXP-037's own already-
archived adjacency data or (b) an independent from-scratch recomputation from raw vertex
coordinates. Shell's five new inner-wall faces are real-adjacent only to the shell's own
directly-modified opening face and to each other — never to any of the five faces whose tokens
EXP-035 established are unchanged.

The full-corpus tally (Part 1) is now clean across all four tested feature types: 0 cases of
"adjacent but unchanged," 0 cases of "changed but not adjacent," for every face-comparison where
archived data exists.

### What remained invariant

Nothing about the fillet/chamfer/hole findings themselves changed — EXP-037's own computed
`added[]`/`matched[]`/`adjacentToModelFaces` data was correct and unmodified throughout; only
the prose interpretation of the shell case in `EXP037_SUMMARY.md`/the 2026-08-14 evidence file
was wrong, and this experiment did not need to touch either the script or the JSON to find or
fix that.

### Interpretation

**Observation**: no feature type tested in this corpus produces a face that is real-adjacent to
newly created geometry yet keeps an unchanged token. **What this does and does not establish**:
it removes the one piece of evidence that had been used to argue against a universal "real
adjacency correlates with a token change" rule. It does **not** newly establish that rule as
universal — shell no longer contributes a disconfirming case, but it also does not contribute a
*new* confirming case beyond what fillet/chamfer already showed, because shell's unmodified
faces are never adjacent to anything new to test in either direction. The adjacency-vs-direct-
modification confound identified in EXP-038 §7 for edge-type features is completely unaffected
by this correction.

### Hypotheses strengthened

- "Token signature changes correlate with real geometric adjacency to modified geometry"
  (FH-031): the specific counter-evidence previously cited against generalizing this past
  fillet/chamfer is retracted. Status remains **Strong Evidence (fillet/chamfer, n=2 edges) —
  not Verified** — this correction removes a piece of contrary evidence, it does not supply new
  confirming evidence sufficient to promote the claim further.

### Hypotheses weakened/falsified

None. This experiment corrects a documentation error; it does not falsify or newly support any
hypothesis beyond retracting the specific "shell counterexample" claim.

### Remaining unknowns

Unchanged from EXP-037/038: the causal mechanism, the adjacency-vs-direct-modification
confound for edge features, generalization beyond vertical edges of a 10mm cube, and everything
in `RESEARCH_HANDOFF.md`'s "Current Unknowns."

### Highest-information next experiment

Not begun here. See `knowledge/RESEARCH_HANDOFF.md` and `NEXT_QUESTIONS.md` for the
horizontal-edge-fillet proposal already on record from EXP-037/038 (edge shared by +X/+Z),
which remains the best-justified next new-model experiment: it breaks the vertical-edge
symmetry pair that makes C03/C12 not fully independent samples, and is the most direct way to
add a genuinely new, non-redundant data point to the n=2 result.

## 5. Anti-Overclaim Notes

- This is a **documentation correction**, not a new geometric finding about SLDPRT. The
  underlying `computeAdjacency()`/`matchFaces()` algorithms and their JSON output were correct
  throughout — verified by reproducing the shell recheck two independent ways (via
  `EXP037_RESULTS.json`'s existing records, and via a from-scratch recomputation) and getting
  the same answer both times.
- **Do not read "shell contributes zero counterexamples" as "adjacency is now proven
  universal."** It removes a specific piece of contrary evidence; it does not add confirming
  evidence beyond what was already established for fillet/chamfer.
- **Do not treat the full-corpus 0/0 tally (Part 1) as n=24 independent confirmations of a
  causal law.** Many of the 24 rows are the same small set of relationships repeated across
  near-identical models (fillet and chamfer are structurally near-duplicates of each other on
  the same cube); the effective sample size for generalization purposes remains small, as
  EXP-038 §7 already notes for the edge-location question specifically.
