## 2. Method

`v0.4.7/exp038_nq028_c12_second_edge.js`:

1. Parses `test files original/controlled/C12_cube_fillet_1mm_edge2/model.SLDPRT` directly,
   using `parser/v0.1/src/parser-core.js` unmodified (read-only). Extracts full per-face
   vertex arrays, Block1 tokens (`b1Body`), Block2 body (`b2Body`), ec/vc/secCount/b1Len, and
   face orientation (via average normal, identical classification function to
   exp032/033/037).
2. Loads C00 (`facesA`) and C03 (`facesB`) from the already-archived
   `VERTEX_ANALYSIS.json['C00_cube_10mm_vs_C03_cube_fillet_1mm']`, and their full Block1 token
   arrays from `EXP033_FEATURE_STATE.json`.
3. Reuses `computeAdjacency()` from EXP-037 **verbatim** (real vertex/edge-sharing adjacency,
   ≥2 coincident vertices = shares an edge).
4. Reuses EXP-037's `matchFaces()` **strategy** (centroid-distance correspondence with explicit
   ambiguity flagging) with one measured, validated refinement — see Section 3.
5. For each pair (C00→C03, C00→C12): computes face correspondence, flags any ambiguity,
   identifies the added (new) face, computes its real within-model adjacency, and compares
   every matched pair's ec/vc/secCount/b1Len/b2Body/full-token-array.
6. Cross-references: for each model, which C00 faces have changed tokens but unchanged
   structural signature (the "signature change without structural change" pattern from
   EXP-033), and whether that set equals the model's own real-adjacency set.

No new Block1/Block2 parsing scheme was invented — the same validated extraction
(`parser/v0.1/src/parser-core.js`, `INV-016/017/018`) used by every prior v0.4.7 experiment is
reused unmodified.

## 3. Tooling Refinement: Bounding-Box Center Replaces Raw Vertex-Average Centroid

**The problem, found while validating against real C12 data (not assumed in advance):**
EXP-037's `matchFaces()` used each face's raw vertex-average position as its "centroid" for
correspondence scoring, with a 0.004m match threshold — validated at the time against C03, C09,
C04, and C10. Applied unmodified to C00 vs C12, it misclassified C00's faces 4 and 5 (+Z/-Z,
which keep the same topological identity across the fillet, just becoming multi-loop) as having
**no** correspondence in C12, incorrectly reporting them as `removed` (from C00) and C12's own
faces 4/5/6 as all `added`.

**Root cause**: raw vertex-averaging is sensitive to non-uniform tessellation density. The
newly-created fillet arc is finely subdivided (many closely-spaced vertices along the curve),
which pulls a face's vertex-average disproportionately toward the arc once that face becomes
multi-loop. Measured directly: C00 face 4 → C12 face 4's vertex-average centroid shifted by
**0.004161m**, and C00 face 5 → C12 face 5 shifted by **0.004613m** — both over EXP-037's
0.004m threshold, and within 0.0001–0.0005m of the ~0.004566m distance separating the genuinely
new face (index 6) from its nearest unrelated existing face. The margin EXP-037 relied on had
collapsed for this specific model's geometry.

**Fix**: use each face's **axis-aligned bounding-box center** — `((minX+maxX)/2, (minY+maxY)/2,
(minZ+maxZ)/2)` — instead of the vertex average. This depends only on a face's spatial extent,
not on how many points happen to be sampled along one edge of it, so uneven tessellation no
longer biases the position estimate.

**Validated across the whole corpus, not just C12**, before adopting the fix (to rule out
tuning the threshold specifically to produce a favorable NQ-028 answer):

| Pair | Max genuine same-face bbox-center shift |
|---|---|
| C00→C03 | 0.0005m |
| C00→C09 | 0.0005m |
| C00→C04 | 0.0000m |
| C00→C10 | 0.0000m for genuine same-face pairs. (A same-*index* comparison for C10 shows 0.0071m, but this is a known artifact: C10's face indices are offset by one relative to C00 due to the shell's inserted opening face at index 0 — established independently in EXP-035, not a real same-face shift. `matchFaces()`'s closest-match correspondence, not raw index, already handles this correctly.) |
| C00→C12 | 0.0005m |

New face's bbox-center distance to nearest unrelated existing face: **0.004528m** (both C03 and
C12, independently). Minimum bbox-center separation between any two distinct C00 faces:
**0.007071m**. A threshold of **0.002m** was adopted — ≥4x the largest genuine same-face shift
(0.0005m), and with more than 2x margin below the nearest new-face/unrelated-face distance
(0.004528m). `EXP037_RESULTS.json`/`exp037_edge_location_and_adjacency.js` are **not** modified
by this finding — the refinement is applied only within `exp038_nq028_c12_second_edge.js`, and
is documented here per the project's append-only/in-place-correction-note convention.

| 3 | +Y | **CHANGED** — vertices shifted, tokens `[1,17,79,0,80,50]`→`[1,139,144,0,79,142]` | UNCHANGED — vertices identical, tokens identical |
| 4 | +Z | Structurally modified: ec 4→6, vc 4→14, secCount 1→3, b1Len 6→22, b2Body changed (multi-loop) | Structurally modified: ec 4→5, vc 4→14, secCount 1→3, b1Len changed, b2Body changed (multi-loop) |
| 5 | -Z | Structurally modified (same pattern as face 4) | Structurally modified (same pattern as face 4) |
| (new, index 6) | NON_AXIS | Added: ec=13, vc=16, secCount=2 | Added: ec=13, vc=16, secCount=2 |

For every row marked **CHANGED** (2/3 in C03; 0/1 in C12): `ecChanged`, `vcChanged`,
`secCountChanged`, and `b1LenChanged` are all **false** — the structural signature is
byte-identical to C00. `b2BodyChanged` is also **false** for these rows (loop structure

shift from the fillet trimming the shared boundary edge. This exactly reproduces EXP-033's
original C03 finding ("signature changes occur without structural changes") and shows the
identical pattern, mirrored to the opposite pair of faces, for C12.

Faces 4/5 in both models show `b2BodyChanged: true` alongside the structural changes (loop
count goes from 1 to 3), consistent with becoming genuinely multi-loop.

Real within-model adjacency of each model's new face (index 6), computed via
`computeAdjacency()` (≥2 shared vertices), translated to C00 face indices via the corrected

| Model | Real adjacency (C00 indices) | Orientations |
|---|---|---|
| C03 | {2, 3, 4, 5} | +X, +Y, +Z, -Z |
| C12 | {0, 1, 4, 5} | -X, -Y, +Z, -Z |

Token-changed-but-structurally-unmodified faces (from Section 4), i.e. the set EXP-033
originally flagged as changing "without adjacency" (a claim the 2026-08-14 audit found
untested — see `knowledge/evidence/2026-08-14_archivist-audit-EXP027-036.md` Finding A):

| Model | Token-changed, structurally unmodified | Real-adjacency set (excl. directly-modified 4/5) | Equal? |
|---|---|---|---|
| C03 | {2, 3} | {2, 3} | **YES** |
| C12 | {0, 1} | {0, 1} | **YES** |

**The three discriminating comparisons NQ-028 was designed to make:**

1. **Same face index changed in both models?** C03: {2,3}. C12: {0,1}. **NO.** Rules out a
   pure serialization-index/face-order explanation (e.g. "the 3rd and 4th face in the array
   always get perturbed").
2. **Same orientation label changed in both models?** C03: {+X,+Y}. C12: {-X,-Y}. **NO.** Rules
   out "the same physical faces of the cube, regardless of feature location" and, combined with
   (1), rules out any fixed positional rule independent of the fillet's actual location.
3. **Does each model's changed set equal its OWN real (vertex-computed) adjacency set?** C03:
   yes. C12: yes. The changed-face set **relocated together with** the fillet, landing exactly
   on the two faces that genuinely border the new edge in each case.

## 6. Final Report

### What was tested

Whether the Block1 token changes previously observed under a fillet on the edge shared by +X
and +Y (C03, established in EXP-032/033) are tied to that specific physical edge location, or
instead recur on the same faces/indices regardless of where the fillet is placed. C12 — a real
SolidWorks model supplied by the user, verified from its own STEP file to be a 1mm fillet on
the edge shared by -X and -Y, all else held identical to C00/C03 — was compared against C00 and
C03 using EXP-037's corrected adjacency and correspondence tooling (with one validated
refinement, Section 3).

### What changed

The set of faces with a changed Block1 token signature but unchanged structural signature
(ec/vc/secCount/b1Len) relocated from {+X, +Y} (C03) to {-X, -Y} (C12) — the two faces
bordering the new fillet's edge in each respective model. Face index of the changed faces also
changed ({2,3} → {0,1}). The two directly, structurally modified faces (formerly +Z/-Z,
becoming multi-loop) are present and analogous in both models.

### What remained invariant

Both C00, C03, and C12 obey `INV-016/017/018` (validated implicitly via `parser-core.js`'s
successful, unmodified parse of all three). The relationship "changed faces = real adjacency to
the new feature face" held in both models — this pattern itself is now observed twice, not
once. The structural signature (ec/vc/secCount/b1Len) of the token-changed-but-not-directly-
modified faces stayed identical to C00 in both models — only token values and (slightly) vertex
positions changed. The new face's own structural shape (ec=13, vc=16, secCount=2) is identical
between C03 and C12.

### Spatial/topological interpretation

**Observation**: the changed-face set moved with the fillet's physical location across two
independently tested, symmetric edges of the same cube. **Interpretation, held to the evidence
available**: this is consistent with Hypothesis A (spatial/topological causation) and
inconsistent with Hypothesis B (global/feature-type state, as originally stated in NQ-028 — "the
same +X/+Y faces change... independent of which edge"). It does **not** prove a causal
mechanism, and — as detailed in Section 7's confound note — it does not distinguish "caused by
genuine topological adjacency to the new face" from "caused by this face's own vertices being
directly (if minutely) modified by the trim," because for an edge fillet those two candidate
triggers pick out the identical set of faces by construction. Resolving that distinction would
require a feature type that creates a new adjacent face without perturbing the neighboring
face's own vertices — not available in this corpus.

### Global-state interpretation

**Observation**: the changed-face set did NOT stay fixed at +X/+Y, and did NOT stay fixed at
face indices {2,3}, when the fillet moved to a different edge. **Interpretation**: Hypothesis B
as literally stated in NQ-028 ("the same faces... change... independent of which edge") is
falsified by this result. A more general "global counter" explanation not tied to a fixed face
or index (e.g. some other global state variable that happens to correlate with edge location)
cannot be ruled out by two data points alone, but no such alternative explanation was proposed
prior to this experiment, and none of the evidence collected here supports one over the
straightforward spatial explanation.

### Hypotheses strengthened

- **Hypothesis A (spatial/topological causation)**, as applied to edge-type features
  (fillet/chamfer): strengthened from "Strong Evidence, one edge" (EXP-037) to "Strong
  Evidence, two independently tested edges, with the changed-face set relocating exactly as
  predicted." Still correlational (Section 7), not proof of mechanism, and n=2 is a small
  sample — but a clean, unambiguous replication at a second location is meaningfully stronger
  than the single-edge result alone.
- "Token signature changes correlate with adjacency to modified geometry" (FH-031's original
  hypothesis, downgraded to Unknown by the 2026-08-14 audit, then to "Strong Evidence, single
  edge" by EXP-037): further strengthened to "Strong Evidence, two edges." Still not Verified.

### Hypotheses weakened/falsified

- **Hypothesis B, as literally stated in NQ-028** ("the same +X/+Y faces change... whenever
  any edge-type feature is applied... independent of which edge"): **falsified**. C12 changes
  -X/-Y, not +X/+Y, when the fillet moves.
- A pure **face-index/serialization-order** explanation ("index 2 and 3 always perturb"):
  **falsified**. C12 changes indices 0 and 1.

### Remaining unknowns

1. **Mechanism.** Why a face genuinely adjacent to (and minutely trimmed by) a newly created
   fillet/chamfer surface receives a different Block1 token value is still unknown. This
   experiment establishes *where*, not *why* or *how*.
2. **Adjacency vs. direct (vertex-level) modification, unresolved (Section 7 confound).** Not
   distinguishable with the feature types available in this corpus.
3. **n=2, both vertical, both on the same cube.** A horizontal edge, a non-cube geometry, or a
   different feature radius/parameter is untested. Generalization beyond "1mm fillets on
   vertical edges of a 10mm cube" is not established.
4. Everything already listed as unknown in `knowledge/RESEARCH_HANDOFF.md` "Current Unknowns"
   and EXP-037's remaining unknowns (Block1/Block2 semantics generally, the `[4,8,2,N]` header,
   why shell's structurally-analogous adjacency does not produce a token change) — unaffected
   by this experiment.

### Highest-information next experiment

**Not recommended here, per instruction** — this session does not begin another experiment.
(For context only, should a future session pick this up: the most direct follow-up would be a
horizontal-edge fillet, e.g. on the edge shared by +X and +Z, to test whether the effect
generalizes beyond vertical edges; a close second would be a feature type that adds a face
adjacent to an existing one without perturbing that existing face's own vertices, to resolve
the Section 7 confound. Neither is begun by this experiment.)

## 7. Anti-Overclaim Notes (consolidated)

- **Observation vs. interpretation, explicit throughout.** Every claim in this file is either
  labeled an observation (a directly computed fact: face indices, orientations, token arrays,
  shared-vertex counts) or explicitly flagged as interpretation (a reading of what the
  observation is consistent/inconsistent with). No claim asserts a proven causal mechanism.
- **Do not treat "Strong Evidence, two edges" as "Verified."** Per `RESEARCH_DASHBOARD.md`
  policy, promotion to `KNOWN_INVARIANTS.md` requires more than a two-data-point correlation,
  however clean. This file recommends no such promotion.
- **Do not cite this experiment as resolving the adjacency-vs-direct-modification question.**
  See Section 7 [this section]/Section 6 "Spatial/topological interpretation" — the two
  candidate mechanisms remain confounded for edge-type features in this corpus.
- **Do not cite this experiment as re-establishing "vertex position change causes token
  change" in general.** EXP-034 already showed whole-model scale/translation (which changes
  every vertex) leaves tokens completely invariant. The effect here is local/topological, not
  a general vertex-coordinate-sensitivity claim.
- **Do not use this experiment's face-count/added-face results as new evidence about hole or
  shell.** Only C00, C03, and C12 (all fillet-family) were analyzed here; EXP-037's hole/shell
  findings are unaffected and not re-tested.
