## Browser verification (manual, headless Chromium via Playwright)

Not a corpus-scale automated test -- a functional smoke test of the actual UI against real files, performed before declaring the viewer functional, per the "start the dev server and use the feature in a browser" requirement for UI work.

Method: served `parser/v0.1/web/` over local HTTP; CDN dependencies (pako, three.js, OrbitControls) substituted with locally-cached copies of the identical files only because this sandboxed environment's headless Chromium could not reach the CDN through the sandbox's proxy (confirmed via direct `curl` through the same proxy succeeding) -- an environment artifact of this session, not a change to the shipped `web/index.html`, which still references the CDN URLs.

**USB hub case BOTTOM.SLDPRT:**
- Parsed correctly: format=openswx, DisplayLists=98,481 bytes, total candidates=156, valid=39, rejected=117, triangles rendered=1,488, unrenderable loops=0.
- Face list populated with 39 entries; selecting face #0 populated the metadata panel correctly (marker=0x17a2, ec=4, vc=4, secCount=1, loopSizes=[4], triCount=2).
- Wireframe/vertices/normals/solid-mesh toggles all functioned without error.
- Screenshot confirms a plausible, recognizable rendered mesh with wireframe, vertex points, and normal lines all visible simultaneously.
- 0 console/page errors.

**Dekor.SLDPRT (larger, multi-loop faces present):**
- Parsed correctly: valid=375, rejected=1,125, triangles rendered=15,282, unrenderable loops=0.
- A `secCount=1044` face (mp=0x2636) selected via the face list; metadata panel showed 1,044 loop sizes and 3,774 rendered triangles.
- Canvas click-to-select (three.js raycasting -> triangle index -> face index mapping) confirmed working: after clicking the canvas, the metadata panel became visible and a face list entry was marked selected.
- Screenshot shows the rendered mesh for this file as a visually chaotic, clearly-implausible starburst pattern -- recorded as the observation behind new open question OQ-019 (see `knowledge/OPEN_QUESTIONS.md`), not treated as evidence of a parser bug (the underlying vertex/normal/offset data for this face independently matches the v0.4.5 reference exactly, per the per-face comparison above).
- 0 console/network errors.

**SW2000-s01.SLDPRT (OLE2, expected-unsupported):**
- Error box displayed the exact unsupported-format message; HUD updated to "Parse failed -- see errors in the sidebar". No silent failure, no crash.

**Known gaps:**
- HEADPHONE (62 faces) untested -- file not present in this repository checkout, same as v0.4.5/v0.4.6.
- Browser verification used locally-cached copies of the CDN libraries due to a sandbox proxy limitation in this session; the shipped `web/index.html` is unmodified and still references the CDN URLs directly (same pattern as the pre-existing `v0.2.2/web/viewer.html`).
- The per-face comparison checks `edgeCount`/`vertexCount`/`secCount` only (not full vertex/normal float-by-float equality), since the v0.4.5 reference JSON does not store raw vertex/normal arrays. Vertex/normal correctness is instead guaranteed structurally: `parser-core.js` reads them at the same offsets established by INV-002, using the same gap/normals-unit-length gates as EXP-021/EXP-024-CORRECTED.
